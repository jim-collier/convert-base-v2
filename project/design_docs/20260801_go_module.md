## Status

Built and working. Split out of `20260731_linkable_library.md`, which covered this, WebAssembly, and a C library in one document. That document stays as the record of the original decision. This one tracks the Go module from here.

The package is not published yet. See [The first tag is not pushed](#the-first-tag-is-not-pushed).

## Introduction

The conversion core is a Go package. Another Go program can import it and convert in process, instead of running the command and reading its output.

That matters because reimplementing this is not a small job. There are sixty-odd bases, tail schemes for the big ones, a tri-state for the marker fields, and constant-memory streaming for every base that can carry raw bytes.

## What exists now

- The module is `github.com/jim-collier/convert-base-v2/lib`, rooted at `github/lib/`. The path matches the directory, which is what makes it fetchable at all. It did not before.

- Four packages live under it. `convertbase` is the library. `cmd/convert-base-v2` is the command. `wasm` is the browser entry point. `shcl` is a vendored config parser.

- The library is Apache-2.0. The command stays GPL-2.0-or-later. The reasoning is in `20260731_linkable_library.md` and is settled.

- The library has its own version, `convertbase.Version`, currently `v0.1.0`. It is deliberately not the command's `v2.x`.

- There are no external dependencies. Standard library plus own source, and no `go.sum`.

- The public surface is `Convert`, `StreamConvert`, `StreamBytesRoute`, `Registry` with `NewRegistry`, `Lookup`, `Register`, `LoadConfig`, `OrderedBases` and `Print`, `Base` with `Finalize`, `Name`, `NegSym`, `DecSym`, `RawCodec`, `Tokenize` and `HasByteDigit`, `Options`, `ApplyOptions`, `ResolveBase`, `ParseSymbolSpec`, `SpecOpts` and `PowerOfTwoBits`.

- The `go` directive in `go.mod` is 1.21. That is a deliberate floor, kept low so distro packagers on an older pinned Go can still build from source.

## End goals

- A Go program can add this as a dependency and get every conversion the command can do.

- Streaming is available to callers, not just one-shot conversion, and stays constant memory.

- The public surface is small enough to hold stable under semantic versioning.

- The library never writes to a stream it does not own, and never touches the caller's filesystem on its own.

The first three are met in substance. The fourth is met. What is left is publishing, and tightening the surface before it becomes a promise.

## The version scheme

Go puts a module's major version into its import path above v1. A library tagged `v2.1.0` would have to be imported as `.../lib/v2/convertbase`.

That is why the package does not share the command's number:

| Option | Effect | Cost
|---|---|---
| Share the command's version | One number to track. | A future convert-base-v3 rewrites the import path. Every caller's code breaks over a change that never touched the package.
| Give the package its own version | The package's number moves only when the package moves. | Two numbers to track.

The package carries its own. Starting at v0 also means no compatibility promise yet, which is the honest signal for an API published for the first time.

Tags are directory-prefixed, `lib/v0.1.0`. The release workflow pushes one only when it is absent, so a release that only touches the command is a no-op for the module.

Keeping the module in a subdirectory is what allows any of this. A `go.mod` at the repository root is versioned by the repository's bare tags, so it would be stuck on the command's number.

## Open items

### The first tag is not pushed

No `lib/*` tag exists. The newest tag in the repository is `v2.0.0`, which is the command.

Until `lib/v0.1.0` is pushed, `go get` cannot resolve a version, so nothing can import this. Any documentation that says the package is available is ahead of the facts.

The release workflow already knows how to push the tag. It runs on a merge to main, and the `lib` branch has not been merged.

### Library errors name command-line flags

Resolved. The library now states these conditions neutrally, as typed errors: an unknown base (with the near-match suggestions, which are useful from any caller), a missing negative or decimal marker on the output base, a default marker colliding with a digit, and a retired in-spec marker token.

The command recognizes each type at its single error sink and appends its own pointer - the `--list` hint, the flag names, the config field. Its output is unchanged, byte for byte. A Go program or a browser page gets the neutral text, and can match on the types to add pointers of its own.

The two options weighed were a neutral message with the command adding its hint, or the library taking a hint string at construction. The first won: it is correct for every caller, and the command already had one place all errors pass through.

### No way to cancel a long conversion

`Convert` is synchronous, and the number path is O(N^2). A large input can run for a long time and the caller cannot stop it.

The command is fine, because a person presses Ctrl-C and the process dies. A library caller has no equivalent. A browser page has no equivalent either, which is why the browser module bounds `precision` instead.

The usual Go answer is a `context.Context` parameter, checked periodically inside the conversion loop. That is a signature change, so it belongs before v1.0 rather than after.

### The finalize ordering trap

For a custom alphabet the marker fields must be set before the first `Finalize`. Otherwise the default `-` collides with a digit and the call fails.

Named bases work the other way around. Copy the base, override, then finalize again.

This has already caused one bug. The library should either make the wrong order impossible, or document it where a caller will actually read it.

### Registry.Print is presentation

`Print` formats a table. Formatting is not a library job.

It stays because it reads unexported fields, so moving it to the command means widening the surface to let the command do the same work from outside. That trade was accepted for now. It is worth revisiting before v1.0, because a v1 surface is harder to shrink.

## What v1.0 would require

v0 promises nothing, which is correct for a first release. Moving to v1.0 means the surface stops changing, so these are worth settling first:

- Cancellation, if it is wanted, because it changes signatures.

- Whether `Print` stays.

- Whether the surface can be smaller. Twenty-odd exported names is a lot to keep stable, and some of them exist because the command needed them, not because a general caller does.

## Testing

The library builds and its tests pass without the command, which keeps a dependency on the command from creeping back in.

The integration harness drives the binary and does not care about package layout, so it covers the library indirectly at full breadth.

The README's Go example is checked to compile and to produce the same output as the command.

## Compatibility

The module path change broke nothing, because nothing could depend on the module before. The repository's bare tags never addressed a module in a subdirectory, so no version of this was ever fetchable.

The command's version is unaffected. Users of the tool have nothing to notice here.
